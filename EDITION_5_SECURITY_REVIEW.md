## 1. الملخص المعماري وأهداف Edition 5 المعدلة

تم تصميم هذه النسخة لتلبية المتطلبات المحددة لإدارة **عمارة سكنية واحدة معتمدة (Single Building Architecture)**:
1. **حصر النظام في عمارة واحدة فقط أمنياً وهيكلياً:** منع إضافة أي عمارة ثانية عبر القواعد الأمنية للفايربيس، ومنع الحذف النهائي للعمارة المعتمدة.
2. **مرونة كاملة لتعديل بيانات العمارة:** يستطيع Super Admin وAssistant Admin تعديل اسم العمارة، وعنوانها، وعدد الأدوار، وعدد الشقق، والخزينة، ومسؤول العقار.
3. **فصل وحماية الشقق والبيانات المالية عند التعديل:** تعديل عدد أدوار أو شقق العمارة لا يؤدي نهائياً إلى حذف شقق أو سكان أو أرصدة.
4. **المدير المساعد كامل الصلاحيات التشغيلية (Full Admin):** يمتلك كامل صلاحيات إدارة شقق وسكان ومدفوعات ومصروفات وصيانة العمارة الواحدة دون أي قيود نطاق.
5. **حماية مالك النظام (Super Admin):** قفل الهوية والبريد المعتمد الموثق، وحصرية إدارة حسابات المديرين، ومنع ترقية أي حساب إلى رتبة السوبر أدمن.
6. **حماية مالية مطلقة:** منع الحذف النهائي لسجلات المدفوعات والمصروفات (`allow delete: if false;`).
7. **خصوصية الساكن والمستأجر:** لا يرى الساكن شقق الجيران، والمستأجر محصور بمدفوعات فترة إقامته فقط.

## 2. التحليل التقني لفرض شرط «العمارة الواحدة» أمنياً (Technical Deep-Dive)

### التحذير التقني وسؤال التزامن (Concurrency & Uniqueness Analysis):
- **هل تستطيع قواعد Firestore Security Rules وحدها ضمان تفرد مستند إذا كانت المعرفات عشوائية؟**
  لا؛ في Firestore، إذا سُمح للمستخدم بإنشاء مستندات بمعرفات عشوائية (مثل `addDoc` أو توليد Auto-ID)، فإن القواعد لا تستطيع فحص إجمالي عدد مستندات المجموعة في زمن حقيقي دون استعلام aggregation مكلف، وتحت التزامن الشديد (Concurrent Requests) قد تُنشأ مستندات إضافية قبل تحديث أي عداد خارجي.
- **كيف حققت Edition 5 ضمان التفرد الرياضي الحاسم (Airtight Deterministic Uniqueness)؟**
  تم اعتماد معمارية **المعرف المعتمد الثابت (Canonical Building ID Pinned to `bld-1`)**:
  ```javascript
  function canonicalBuildingId() {
    return 'bld-1';
  }

  function isCanonicalBuilding(bldId) {
    return bldId == canonicalBuildingId();
  }
  ```
  1. **قفل المسار (Document Path Pinned):**
     القواعد لا تسمح بالإنشاء إلا إذا كان مسار المستند مساوياً حصراً لـ `/buildings/bld-1`. أي طلب كتابة موجه إلى أي معرف آخر (مثل `bld-2` أو أي معرف عشوائي) يتم **رفضه فوراً بـ Permission Denied** بغض النظر عن هوية المرسل.
  2. **طبيعة المعرفات في Firestore (Key Uniqueness):**
     في أي قاعدة بيانات NoSQL / Firestore، لا يمكن أبداً وجود مستندين يحملان نفس المسار `/buildings/bld-1`.
  3. **منع إعادة الإنشاء (Preventing Recreation):**
     يشترط مسار الإنشاء الأولي (Bootstrap):
     ```javascript
     allow create: if isSuperAdmin() &&
       buildingId == canonicalBuildingId() &&
       !exists(/databases/$(database)/documents/buildings/$(canonicalBuildingId())) && ...
     ```
     بمجرد إنشاء مستند العمارة المعتمدة `bld-1`، فإن شرط `!exists(...)` يصبح غير متحقق بصفة دائمة، وتُقفل نافذة الـ `create` نهائياً أمام الجميع (بما فيهم Super Admin).
  4. **منع الحذف نهائياً (Absolute No-Delete Constraint):**
     تم قفل عملية الحذف تماماً:
     ```javascript
     allow delete: if false;
     ```
     لا يستطيع أي مستخدم أو مدير حذف العمارة، مما يمنع تفريغ المسار أو محاولة إعادة إنشائه.
  5. **النتيجة المحققة:**
     بهذا القيد الثلاثي (المعرف الثابت + التحقق من عدم الوجود المسبق + منع الحذف نهائياً)، يستحيل رياضياً وبرمجياً أن يتجاوز عدد العمارات في قاعدة البيانات مستنداً واحداً فقط، حتى مع آلاف الطلبات المتزامنة خارج التطبيق.

## 3. تعديل بيانات العمارة دون حذف الشقق والبيانات (Data Decoupling)

تم تصميم قاعدة تحديث العمارة لتتيح المرونة الكاملة للمديرين:
```javascript
allow update: if isAdmin() &&
  buildingId == canonicalBuildingId() &&
  incoming().id == canonicalBuildingId() &&
  incoming().diff(existing()).affectedKeys().hasOnly([
    'name', 'address', 'totalFloors', 'totalUnits', 'balance',
    'monthlyTarget', 'reserveFund', 'managerName', 'managerPhone', 'updatedAt'
  ]);
```
- **حماية الشقق والسجلات:**
  في معمارية Cloud Firestore، مستندات الشقق في `/apartments` ومستندات المدفوعات في `/payments` مخزنة في مجموعات منفصلة ومستقلة.
  تعديل حقل `totalFloors` أو `totalUnits` في مستند `/buildings/bld-1` هو مجرد تعديل على حقول ذلك المستند فقط، ولا يؤثر بأي شكل من الأشكال على وثائق الشقق القائمة أو أرصدتها أو سكانها.

## 5. حماية خصوصية السكان وسجلات المدفوعات

1. **حظر استعراض الشقق للسكان:**
   في `/apartments/{apartmentId}` تم قصر الـ `list` على المديرين:
   ```javascript
   allow list: if isAdmin();
   ```
   بينما يُسمح للساكن بقراءة شقته فقط عبر `get` ومطابقة معرف الشقة:
   ```javascript
   (isApprovedResident() && currentUserData().apartmentId == apartmentId)
   ```
2. **عزل فترات إقامة المستأجرين:**
   المستأجر لا يرى إلا المدفوعات التابعة لفترة إقامته:
   ```javascript
   paymentData.date >= currentUserData().leaseStartDate
   ```
   ويُحجب عنه أي سجل يخص المالك أو المستأجرين السابقين للشقة.
3. **منع الحذف المالي نهائياً:**
   في مجموعتي `payments` و`expenses`:
   ```javascript
   allow delete: if false;
   ```
   تظل جميع السجلات المالية غير قابلة للحذف نهائياً، ويتم التعامل مع الأخطاء عبر عمليات تصحيح أو إلغاء موثقة في سجلات التدقيق `payment_audit_logs`.
